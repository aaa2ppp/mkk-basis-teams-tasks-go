### Рефакторинг тестов: разделение по слоям

#### Текущая ситуация
В настоящее время тесты (`task_update_test.go`, `task_list_test.go`, `task_create_test.go`, `team_test.go` и др.) используют реальное хранилище и реальную БД (через `testcontainers`). Это интеграционные тесты, которые проверяют весь стек: сервис → хранилище → СУБД. Такой подход оправдан на начальном этапе, но имеет следующие недостатки:

- **Смешение ответственности**: Ошибка может быть как в сервисе (бизнес-логика), так и в хранилище (SQL-запросы). Тест не позволяет быстро понять, какой слой виноват.
- **Скрытие дефектов**: Если сервис перехватывает ошибку до вызова хранилища, мы не узнаем, что хранилище может быть уязвимо (например, допускает вставку роли `owner`).
- **Медленное выполнение**: Каждый тест поднимает контейнеры БД и Redis, что замедляет CI/CD.
- **Сложность отладки**: Логи теста смешивают выводы разных слоёв.

#### Предлагаемое решение
Разделить тесты на два уровня:

**1. Юнит-тесты для сервиса (пакет `service`)**
- Тестируют только бизнес-логику и валидацию.
- Внешние зависимости (хранилище, кеш, транзактор) заменяются моками (например, с использованием `mockgen` или ручных заглушек).
- Проверяют:
  - Правильность проверок прав (роли, поля, доступность).
  - Преобразование ошибок из хранилища в доменные ошибки.
  - Валидацию входных параметров (ограничения, обязательность).
  - Обработку специфических случаев (конфликт версий, not found и т.д.).
- Выполняются быстро и не требуют внешних ресурсов.

**2. Интеграционные тесты для хранилища (пакет `storage`)**
- Тестируют только слой доступа к данным: корректность SQL-запросов, ограничения целостности, транзакционность.
- Используют реальную БД (через `testcontainers`), но **вызывают методы хранилища напрямую**, без участия сервиса.
- Проверяют:
  - Что `SELECT` возвращает только данные, доступные пользователю (с учётом `JOIN` с `team_members`).
  - Что `INSERT`/`UPDATE`/`DELETE` корректно применяют ограничения (например, нельзя вставить `owner` через `AddMember`, если это запрещено).
  - Что оптимистическая блокировка работает (обновление с неверной версией не меняет запись).
  - etc
- Эти тесты медленнее, но их меньше, и они целенаправленно проверяют самый надёжный уровень (базу).

**3. Сквозные интеграционные тесты (опционально)**
- Несколько ключевых сценариев (например, полный цикл создания задачи и её обновления) могут остаться как smoke-тесты для проверки взаимодействия слоёв.
- Их количество должно быть минимальным, чтобы не дублировать проверки.

#### Как перестроить существующие тесты

1. **Выделить логику хранилища** из `task_update_test.go` и подобных:
   - Создать `storage/task_test.go`, `storage/team_test.go` и перенести туда прямые вызовы методов хранилища.
   - Модифицировать тесты, чтобы они проверяли только поведение хранилища (ожидание ошибок или успеха на основе входных данных).
   - Использовать вспомогательные функции `InsertUser`, `InsertTeam` и т.д. для подготовки данных.

2. **Переписать тесты сервиса** с использованием моков:
   - Определить интерфейсы для хранилища (если ещё не сделано) и кеша.
   - Создать моки (вручную или генератором).
   - Для каждого теста настроить ожидаемые вызовы мока и возвращаемые значения.
   - Проверить, что сервис обрабатывает их корректно (возвращает нужный результат или ошибку).

3. **Оставить несколько сквозных тестов** в отдельном пакете (например, `e2e_test.go`) для проверки полной связки.

#### Приоритетность
- Начать с выделения интеграционных тестов для хранилища (они наиболее критичны, т.к. база — последний рубеж).
- Затем переписать тесты сервиса на моки.
- Сквозные тесты оставить на потом.

#### Ожидаемые улучшения
- Быстрое выполнение юнит-тестов (менее 1 секунды).
- Чёткое разделение ответственности: ошибка в хранилище не маскируется сервисом и наоборот.
- Упрощение поддержки: при изменении SQL-запроса достаточно обновить только интеграционные тесты, а юнит-тесты сервиса останутся без изменений (если интерфейс хранилища не меняется).

#### Сроки
- Рефакторинг не является срочным, можно выполнять параллельно с основной разработкой.
- Рекомендуется выделить несколько спринтовых задач на поэтапный переход.
