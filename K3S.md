# Локальный запуск в k3s

В каталоге `k3s/` находятся манифесты и Makefile для развёртывания всех компонентов приложения в лёгком Kubernetes-кластере **k3s**. Это позволяет работать в среде, максимально приближенной к продакшену, но локально.

## Предварительные требования

- Установленный [k3s](https://k3s.io/) (однонодовый кластер).
- Утилиты: `kubectl`, `docker`, `envsubst` (входит в пакет `gettext`).
- Доступ к сокету containerd: `/run/k3s/containerd/containerd.sock` (требуется запись).  
  Обычно это решается либо через `sudo`, либо настройкой прав через отдельную группу.  
  Если выбираете группу — создайте свою, **никогда не добавляйте** себя в группу `root` и **никогда не используйте** `chmod 666` — это грубое нарушение безопасности.

## Использование

Команды можно выполнять из каталога `k3s/`:

```bash
cd k3s
make <цель>
```

Либо использовать флаг `-C` для вызова из корня проекта:

```bash
make -C k3s <цель>
```

### Основные цели Makefile

**В разделе «Основные цели Makefile» замените таблицу на:**

| Цель          | Описание |
|:--------------|:---------|
| `make all`    | Полный деплой: сборка образов, загрузка в containerd, создание namespace (при первом запуске), применение ConfigMap/Secret (Secret генерируется автоматически и только при первом запуске), запуск PostgreSQL (StatefulSet при первом запуске), выполнение миграций (Job) и развёртывание сервера (Deployment). |
| `make update` | Горячее обновление сервера: пересборка образа, загрузка в containerd и перезапуск Deployment (без пересоздания базы и миграций). Работает только после успешного выполнения `make all`. |
| `make destroy`| Полное удаление namespace со всеми ресурсами (включая данные базы). Требует подтверждения. |
| `make status` | Показать текущее состояние ресурсов в namespace. |
| `make help`   | Список основных целей. |


Переменные можно переопределить при вызове `make`:

- `NAMESPACE` – имя пространства имён (по умолчанию `teams-tasks`).
- `TAG` – тег Docker-образов (по умолчанию `v0.0.1`).
- `REPLICAS` – количество реплик сервера (по умолчанию `3`).
- `TIMEOUT` – таймаут ожидания готовности подов (по умолчанию `60s`).
- `SERVER_NODE_PORT` – внешний порт NodePort для доступа к серверу (по умолчанию `30080`).

Пример:

```bash
make all NAMESPACE=myapp TAG=v1.0.0 REPLICAS=2 SERVER_NODE_PORT=30081
```

### Доступ к серверу

После успешного деплоя сервер будет доступен по адресу:

```
http://localhost:<SERVER_NODE_PORT>
```

По умолчанию `SERVER_NODE_PORT=30080` (если не переопределён).

### Особенности

- **Пароль базы данных** генерируется автоматически при первом запуске (`make env-init` или `make all`) и сохраняется в Secret `db-secret`.
- **Миграции** выполняются отдельным Job `migrate` после того, как PostgreSQL станет готов к приёму соединений.
- **Данные базы** сохраняются в PersistentVolumeClaim. При удалении namespace данные теряются, при обычном перезапуске (`make all` или `make update`) они остаются нетронутыми.
- Все переменные окружения для приложения берутся из ConfigMap `app-config` и Secret `db-secret`, поэтому файл `.env` в этом сценарии не используется.

## Устранение неполадок

- **Ошибка доступа к сокету containerd** – проверьте права на `/run/k3s/containerd/containerd.sock`. Для решения используйте `sudo` или настройте доступ через отдельную группу. **Категорически не рекомендуется** добавлять себя в группу `root` или выставлять права `666`.
- **Job миграции завершается с ошибкой** – выполните `kubectl logs -n <namespace> job/migrate` для просмотра логов.
- **Сервер не поднимается** – проверьте статус подов: `kubectl get pods -n <namespace>` и логи: `kubectl logs -n <namespace> deployment/server`.

## Полезные инструменты

Для удобной работы с кластером рекомендуется использовать [k9s](https://k9scli.io/) — терминальный интерфейс для управления Kubernetes. Он позволяет быстро просматривать состояние подов, логов, событий и выполнять основные действия без постоянного ввода `kubectl` команд.

Установка и использование описаны в официальной документации.
